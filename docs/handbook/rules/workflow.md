# Professional Contributor & Engineering Workflow Standards

This document establishes the mandatory operational rules and workflow standards for contributing to repositories operating under the Formal Project Bootstrap doctrine. Every action taken by engineers or autonomous agents must adhere to these standards to project uncompromising craft, precision, and professional consistency.

---

## 1. The Clean Public Engineering Persona

Every commit, branch, pull request, issue comment, and code review must reflect the standards of a senior systems engineer:

- **Attribution & Authorship**:
  - Author: Zach Shallbetter (`Zach Shallbetter <zachshallbetter@icloud.com>`).
  - **Zero AI Attribution**: Strictly forbid `Co-Authored-By` trailers, "Generated by AI" footers, assistant session identifiers, or tool names anywhere in code, commit history, documentation, or public GitHub comments.
- **Tone & Communication Voice**:
  - Direct, technical, active-voice human engineering prose.
  - Zero promotional puffery, marketing jargon, sycophancy, emotional filler, or apologies.
  - State the problem, technical rationale, exact changes, verified facts, and concrete test numbers plainly.

### Rule 1.1: Grounded References (No Uncited Claims)
- Never say *"the work I have been doing"* or make unreferenced claims about ongoing efforts.
- Always provide explicit markdown links to the exact pull request, issue, or commit: e.g. `[org/repo#9](https://github.com/org/repo/pull/9)`.

### Rule 1.2: Natural Punctuation & Tone (Zero Em-Dash Crutches)
- Avoid stylistic AI tells such as overusing em-dashes (long dashes), academic thesis headings, and nested bullet boilerplate.
- Write natural, direct sentences using standard punctuation (periods, commas, colons).

### Rule 1.3: Natural Language Over Synthetic Identifiers
- Strictly forbid inventing private, synthetic tracking codes.
- Use standard, discoverable tooling and domain terminology (`cargo test`, worktree isolation, dirty snapshotting).

### Rule 1.4: Natural Engineering Voice (Avoid Predictable Rhetoric)
- Avoid repetitive contrast formulas such as opening paragraphs with *"However, this introduces..."*, *"While X is correct, Y remains..."*, *"The concern is not X, but Y"*, or *"This is not X; it is Y"*.
- State findings, questions, and observations directly without defensive or academic framing.
- Acknowledge author fixes cleanly without immediately tacking on a new theoretical concern.

### Rule 1.5: Vocabulary Discipline & Action Over Abstraction
- Favor direct verbs over abstract noun phrases:
  - Say *"test it"* instead of *"establish a qualification mechanism"*.
  - Say *"decide which crate owns it"* instead of *"resolve the ownership boundary"*.
  - Say *"keep existing behavior working"* instead of *"preserve behavioral compatibility"*.
  - Say *"agree on what the API should do"* instead of *"reconcile the implementation contract"*.
- Avoid dense clustering of formal buzzwords (`boundary`, `contract`, `invariant`, `qualification`, `provenance`, `surface`, `canonical`). Use simpler everyday terms (`separation`, `API`, `rule`, `testing`, `source`, `standard`).

### Rule 1.6: Calibrated Authority & Honest Formulations
- Distinguish verified facts, risks, suggestions, and policy with exact language:
  - *"This fails when..."*: Verified defect with code or test reproduction.
  - *"This may fail when..."*: Hypothesized risk needing investigation.
  - *"Could we consider..."*: Design suggestion or technical preference.
  - *"The repository requires..."*: Verified public policy.
  - *"I recommend..."*: Personal technical judgment.
- Never present personal design preferences or unmerged proposals as established repository rules.

### Rule 1.7: Three-Tier Review Grading & Actionable Focus
- Structure pull request reviews around three distinct categories:
  1. **Blocking**: A demonstrated bug, security vulnerability, broken build, or compatibility break that must be resolved prior to merge.
  2. **Non-blocking**: A worthwhile optimization, cleanup, or ergonomics note that the author can address now or defer.
  3. **Architectural follow-up**: A broader design consideration that belongs in a separate issue or RFC rather than blocking the immediate PR.
- Avoid excessive completeness in PR reviews. State the finding, explain the concrete consequence, and ask an actionable question rather than delivering an exhaustive multi-page essay.
- Stop repeating the same argument once an author has acknowledged it; ask for a specific decision.

### Rule 1.8: Zero Conversational Padding & Wordy Openings
- Avoid polite meta-praise, flattering preamble, and wordy opening formulas.
- Never spend sentences on conversational warm-ups, performative gratitude, or deference.
- Jump straight into the technical facts, corrections, or proposals in the very first sentence.

## 2. Git Hygiene & Zero-Noise Issue Timeline Protocol

GitHub's issue activity feed is an **append-only audit log**. Pushing commits containing `#<issue>` permanently records timeline events (`added N commits that reference this issue`) that cannot be deleted or hidden, even after squashing or force-pushing.

To maintain pristine, professional issue threads and commit history, follow this protocol:

### Rule 2.1: Local-First Iteration & Scratch Commits
- Perform all exploratory, iterative, and scratch work locally.
- **Never include `#<issue>` or `refs #<issue>` in intermediate scratch commits.**
- Scratch commits (*"wip"*, *"fix lint"*, *"address review"*) must never be pushed to a public PR branch.

### Rule 2.2: Single Cohesive Commit Per PR
- By default, every feature or bugfix pull request branch must contain **exactly one cohesive, squashed commit** before opening the PR or requesting review.
- Multi-commit branches are permitted **only** for large multi-crate architectural extractions where every individual commit compiles independently, passes all quality gates, and represents an isolated logical milestone.

### Rule 2.3: Issue Reference Placement
- Issue reference tags (`closes #<issue>` or `fixes #<issue>`) belong strictly in two places:
  1. The **subject or body of the final squashed commit**.
  2. The **Pull Request description** (`Closes #<issue>`).
- This guarantees that GitHub links the PR to the issue cleanly and auto-closes it upon merge without cluttering the issue conversation feed with dozens of transient commit SHAs.

### Rule 2.4: Always Rebase on `origin/main` Before Pushing
- Before pushing a new branch or pushing updates to a PR branch, always fetch and rebase on the latest `origin/main`:
  ```bash
  git fetch origin main
  git rebase origin/main
  ```
- Ensure zero merge conflicts and that the proposed change integrates seamlessly with newly landed upstream commits.

## 3. Pull Request Standards

Every pull request must be structured for immediate, low-friction review by maintainers:

### Rule 3.1: Commit Title & Body Architecture
- **Title**: Imperative mood, under 72 characters, prefixed by crate/module scope where appropriate (e.g. `core: Fix buffer overflow in packet parser`).
- **Body**: Three clean, concise sections:
  1. **Problem**: What defect or gap exists, why it matters, and who is affected.
  2. **Solution**: What architectural or code change was made, how it solves the problem, and non-obvious trade-offs.
  3. **Verification**: Concrete commands run, tests executed, and evidence observed.

### Rule 3.2: Never Claim Completion Without Supporting Evidence
- Never declare work complete without running the strongest practical verification gate.
- Document exact command lines, output excerpts, and assertion counts.
